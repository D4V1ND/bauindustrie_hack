LV Result File

For the frontend team · what each step adds, and how the file looks after it

One file per new LV, one list inside it. lv price writes data/out/<project>.json. Its items list has one entry per line item, and every step adds its fields to that same entry. Nothing has to be joined afterwards.

Every value on this page is real: item P5/02.0001, "Asphalt schneiden, bis 15 cm", followed through all five steps.

  1. Step 0 · ReadThe LV's own data: texts, quantity, unit.
  2. Step 1 · LabelOne field: group.
  3. Step 2 · SortItem type, trade and the reason.
  4. Step 3 · PriceThe prediction and the summary.
  5. Step 4 · RiskThe risk and the risk_summary.

Part 1 · Steps 0 and 1

Read and label

Before step 2 the file holds the LV as it was read, plus one label per item. The fields of later steps are already there, empty.

Code Both steps are deterministic. No AI is involved.

What gets added

FieldTypeMeaning
projectstringShort project ID the person chose, here "P5".
name, date, source_filestring, date or null, stringFrom the LV file's header. Texts can hold anonymiser tokens such as [PROJEKT_004].
pricedbooleanWhether the file itself came with prices. false for a new LV.
items[]arrayOne entry per line item, in LV order. Every field below sits on each entry.
idstringProject + / + item number. Unique across all projects, so use it as the key.
ozstringThe item number (Ordnungszahl) as printed in the LV.
sectionarray of stringsSection titles, outermost first.
short_text, long_textstringThe item's two texts as written in the LV.
quantity, unitnumber or null, stringUnits have one spelling: St, m, m2, m3, h, psch.
unit_price, total_pricenullEmpty in a new LV. The tool never fills them, so never show them as the predicted price.
kind"normal" or "optional"Optional items (Bedarfspositionen) are listed but not added to totals.
read_by"gaeb" or "pdf"Where the texts were read from.
group Step 1stringA 12-character label. Items with the same label are word for word the same item. P5 has no repeats; P4 has 7 sets covering 16 items.

The empty values have fixed shapes: "" for the three step 2 texts, [] for item_types, null for prediction and summary. A file from lv price --copy-only stays without item types.

Part 2 · Step 2

Sort into types

The LV gets its own list of item types, and every item gets one of them with its trade and a reason.

AICode Claude proposes the list and assigns the items. Code checks every answer.

What gets added

FieldTypeMeaning
item_types[]array of {name, trade, description}The LV's own list of item types, proposed once per LV. P5 has 20, P4 has 72. The list can differ from run to run.
item_typestringOne name from item_types, or "Sonstiges" (other) if none fits.
tradestringThe trade of that type, from a fixed list of 17 stand-in names.
item_type_reasonstringOne English sentence on why the item got this type.
For an overview screen
  • The tree "trade, then item type, then quantities" is not stored. Group items by trade and item_type.
  • Add up quantity per unit, never across units, and only for items whose kind is "normal".
Part 3 · Step 3

Look up a price

Every item gets a prediction, and the LV gets a summary. Here: €17.90 per metre, × 70 m = €1,253.00.

CodeAI Code searches and calculates. Claude only judges whether two texts describe the same thing, and never sees a price.

What gets added

FieldTypeMeaning
prediction.methodone of fiveHow the result came about. The next table says what to show for each.
mediannumber or nullThe price to show, per unit. Set only for copied, similar and adjusted.
min, max, mean, countnumber or null; integerRange, average and number of the past prices behind the price. count is 0 for reference and none.
sources[]array of sourcesThe past items the price rests on. For reference: the related items shown in place of a price.
judged[]array of sourcesThe 3 best candidates, best first, each with a why. The judge reads 5; the file keeps 3. Empty when the judge was not asked.
reasonstringOne sentence from the judge, or a fixed sentence when code decided alone.
rule, calculation, resultstring, string, number; else nullOnly for adjusted, e.g. "linear interpolation by DN", "80 + (125 - 100) / (150 - 100) x (120 - 80)", 100.0.
judged_itemstring or nullSet when this item is identical to another item of the LV: the id of the item that was actually judged.
summaryobjectPer method the number of items and their money, and the LV's total: median × quantity over normal items with a price.

What each method means for the screen

MethodWhenShow
copiedA past item is word for word identical.median as the price, marked exact.
similarThe judge called at least one past item the same thing.median as the price, with every source.
adjustedThe same thing exists in a smaller and a larger size. Code interpolates.median, both sources and calculation.
referenceOnly related past items were found.No price. sources as "related, not the same".
noneNothing usable.No price.

One source, in sources and in judged

FieldTypeMeaning
idstringThe past item, e.g. "P2/05.01.0003". The part before / is the past project.
short_textstringIts short text, so no library file is needed to show it.
unit_pricenumberIts price in that past project.
verdictone of fiveexact: copied without a judge. same: the same thing. size_only: the same thing in another size. type_only: the same kind, other material or scope. different: another product or work.
differencestringA few words from the judge on what differs. Empty when nothing does.
whystringOne sentence from the judge. For same: why this is the match. For every other verdict: why it is not.

The item's own unit_price is still null. The looked-up price lives in prediction.median and nowhere else.

Part 4 · Step 4

Score the risk

Every item gets a risk from 0 to 100, and the LV gets a risk_summary. Here: 19 for the item, 51 for all of P5.

CodeAI Code scores the price risk and does the weighting. Claude reads each text and says whether it is complete enough to price.

What gets added

FieldTypeMeaning
risk.scoreinteger, 0 to 100The item's risk. 0.6 × price_risk + 0.4 × description_risk. A place on a scale, not a probability.
price_risk, price_reasoninteger, stringHow unsure the price is, from the step 3 method, with one fixed sentence saying why.
description"complete", "gaps", "vague" or nullDoes the text state what an estimator needs to price the item? null when it was not checked; the score is then the price risk alone.
description_risk, description_reasoninteger or null, stringThe verdict as a number, and one sentence from the model.
missing[]array of stringsWhat the text does not state, at most 3 short phrases. Empty for complete.
valuenumber or nullRoughly what the item is worth. It weights the LV's score. Never show it as a price.
value_basisone of threeprice: found price × quantity. reference: middle price of the related items × quantity. assumed: the value of a typical item.
risk_summaryobjectscore: the items' scores weighted by value, over the normal items. value: the sum of those values. basis: how many items per value basis.

The scale

PartValueRisk
Price riskcopied5
similar25, or 40 when its past prices lie more than 10% apart
adjusted45
reference75
none100
Description riskcomplete10
gaps50
vague90

These are starting values, to be tuned with the estimator. A score says where an item sits on this scale. It is not the chance that a price is wrong.

One list. Every step adds to the same entry.

Part 5 · The second file

The judge log

Next to the result file sits <project>_judge.json: one entry per judge call, for a "why?" view.

Part 6

Rules for the screen

Eight rules that keep the screen honest about what the tool found.

RuleWhat it means
The price is prediction.medianOnly when method is copied, similar or adjusted. Show min to max and count next to it when count is above 1.
Every price shows its sourceFor each entry in sources: id, short_text, unit_price. Tracing a price back is a hard requirement of the estimators.
No price for reference and noneNever fill one in from judged or sources.
judged is ordered best firstAt most 3 entries. If the first one's verdict is same, it is the match and its why says why. Every other entry's why says why it is not the match.
Totals come from summaryOptional items and items without a price are already left out there.
A risk score comes with its reasonsShow price_reason, description_reason and missing next to risk.score. Sorting by score × value puts the items that matter most first.
risk.value is not a priceIt is a weight. Show risk_summary.basis next to the LV's score, so a reader sees how many values are assumed.
Past prices can be near zeroOne candidate in the example costs 0.50 per metre. Some bids hold symbolic prices, and no rule handles them yet.
Not in the file yet
  • The estimator's own decision. There is no field for an accepted or changed price. A field next to prediction, such as final_price, would have to be agreed.
  • The plan findings. With a construction plan, lv price … --plan writes a second file, <project>_plan.json: quantity findings and a spot on the plan for each item, joined to this file by oz, plus an overview of the plan with every item numbered (PNG and Excel). Its shape is in docs/result-format.md.
  • Money per trade or item type. summary splits by method only. Add up median × quantity per trade if a screen needs it.

Bottom line

Build against data/out/P5.json or P4.json. Both are in the current shape. Read items, show prediction.median with its sources when the method has a price, and open the judge log for the "why?".
